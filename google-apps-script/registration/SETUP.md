# 행사별 참가 신청서 — 적용 안내

## 동작
- `협회 행사 신청서 / 2027 / 01월 … 12월 / YYYY-MM-DD 행사명 참가 신청` 구조입니다.
- 행사 날짜를 기준으로 연도·월 폴더를 생성합니다. 같은 일정 저장·재시도는 동일한 폼을 재사용합니다.
- 제목 수정은 폼 이름을 갱신하고, 날짜 변경은 해당 연도·월 폴더로 폼을 이동합니다.
- 신청받기를 끄고 저장·게시하거나 일정을 삭제·게시 취소하면 해당 행사 전용 폼의 접수를 닫고 휴지통 이동을 시도합니다. 공유 폼의 휴지통 이동 권한만 부족한 경우 파일을 보관하고 `trashPending:true`로 저장을 허용합니다. 그 외 오류는 계속 저장·삭제를 중단합니다.
- 같은 일정에서 다시 신청받기를 켜면 휴지통의 동일한 폼을 복원하여 응답을 유지합니다. Drive에서 영구 삭제된 폼은 자동 복원할 수 없습니다.
- CMS 삭제와 Google 작업은 하나의 원자적 트랜잭션이 아닙니다. Google 처리 후 CMS 저장이 실패하면 같은 일정으로 다시 시도합니다.
- 기존 연도별 공용 폼은 다른 행사·응답이 있으므로 삭제하지 않습니다. 새 구조로 전환할 때 해당 행사 선택지만 제거하고, 기존 응답은 행사 명단에서 계속 조회할 수 있습니다.
- 폴더/폼의 공유 권한은 자동으로 확대하지 않습니다. 기본적으로 생성 계정이 관리하며, 다른 운영자에게 필요한 Drive·Forms 접근 권한은 별도 승인 후 설정합니다.

## 실제 Google 적용 순서 (홈페이지 push만으로 적용되지 않음)
1. 기존 KSIS 신청 관리 연결 프로젝트의 Code.gs를 이 폴더의 Code.gs로 교체합니다.
2. 프로젝트에 PerEvent.gs 파일을 추가하고 이 폴더의 PerEvent.gs 내용을 저장합니다.
3. appsscript.json을 이 폴더의 최신 파일로 교체합니다. 기존 forms/email 외 Drive 권한이 필요합니다. 스크립트 속성의 기존 권한·연도별 폼 정보는 지우지 않습니다.
4. 기존 API 실행 파일 배포를 새 버전으로 갱신합니다. 배포 ID와 기존 접근 설정을 유지합니다.
5. 홈페이지 변경을 배포한 뒤 관리자에서 신청받기를 켜고 추가 Drive 권한에 동의합니다.
6. 테스트 일정을 만들어 연도/월 폴더와 전용 폼 생성, 두 번 저장 시 중복 없음, 신청받기 끄기 시 휴지통, 재활성화 시 동일 폼 복원, 일정 삭제 시 휴지통 이동을 실제 Google에서 확인합니다.
7. 실제 운영 일정은 위 검증 후 전환합니다. 기존 신청서는 일정을 다시 저장·게시할 때 전환됩니다.

새 클라이언트는 capabilities(schemaVersion:4)를 먼저 확인합니다. 서버가 구버전이면 Google 변경 요청을 보내기 전에 중단합니다.
개별 응답 삭제는 기존 확인 절차를 유지합니다. 폼 휴지통 이동과 응답 영구 삭제는 별개의 작업입니다.

- 운영 Decap 관리자에서 같은 테스트 일정의 신청받기 켜기 후 저장, 끄기 후 저장도 확인했습니다. 검증 변경은 초안으로 저장하며 검증 중 공개 게시를 실행하지 않습니다.

## 신규 생성 간헐 실패 조사 (버전 11)
- 편집기에서 독립된 신규 폼 6건 생성은 성공했고 테스트 폼은 종료 후 휴지통으로 정리했습니다. 이 결과가 운영 API 실행의 간헐 실패 해결을 의미하지는 않습니다.
- 운영 관리자에서 추가 재현 시 로그인 갱신이 LOGIN_TIMEOUT으로 끝났고 해당 요청은 API 실행 기록에 도착하지 않았습니다. 이전 9~14초 실행 후 실패한 요청과 구분합니다.
- 버전 11은 원인을 확인하기 위한 기록만 추가합니다. 실패하면 비공개 Script Properties의 KSIS_LAST_SYNC_FAILURE에 마지막 한 건의 시각·행사 ID·단계·예외 문구(최대 500자)를 보관합니다. 성공한 재시도가 실패 기록을 지우지 않습니다.
- 요청 본문, 신청자 명단, 응답, OAuth 토큰은 기록하지 않습니다. 원래 예외를 그대로 다시 던지고 기존 잠금과 접근 검사를 유지합니다. 새 폼을 생성하는 재시도 처리는 추가하지 않았습니다.

## 신규 참가비 질문 오류 재현 및 수정 (버전 12)
- 운영 관리자에서 기본 질문과 기본 참가비 양식으로 신규 일정을 저장하여 CONNECTION_FAILED를 재현했습니다. 기록된 단계는 fee-question, 원래 예외는 item.asListItem is not a function입니다.
- addListItem()은 이미 ListItem을 반환하며 일반 Item의 asListItem() 메서드가 없습니다. 질문 ID가 저장된 다음 실패하므로 재시도에서 getItems()로 일반 Item을 읽으면 성공하는 현상이 생겼습니다.
- 새 참가비 질문과 추가 질문 모두 getItemById()로 일반 Item을 얻은 뒤 유형 변환하도록 수정했습니다. 테스트 모형도 생성 결과와 조회 결과의 실제 API 차이를 반영했고, 새 참가비 폼과 네 가지 추가 질문 유형의 첫 저장 회귀 검증을 추가했습니다.
- 기존 배포 ID와 접근 설정을 유지한 실제 버전 12에 수정 반영했습니다. 별도로 발생한 GitHub 중복 검사 오류와 LOGIN_TIMEOUT은 이 예외와 구분합니다.
- 운영 CMS에서 이전 실패 일정의 저장과, 별도 신규 일정(기본 질문 + 기본 6등급 참가비)의 첫 저장 모두 성공했습니다. 공개 게시 없이 진단용 초안 3개를 남겼습니다. 관련 자동 테스트 30개 통과 및 git diff --check를 확인했습니다.
